# ADR 0001: Move BeastyPage from Convex to PostgreSQL with Drizzle

- Status: accepted for implementation; production cutover not yet approved
- Date: 2026-10-15
- Issues: #105 (epic), #106–#117
- Inventory: [`convex-inventory.md`](convex-inventory.md), regenerated by
  `pnpm --dir frontend run migration:inventory`

## Context

Convex is the last usage-billed managed service in the stack. The refreshed
inventory (generated from source, not from the issue text) shows a larger
footprint than the epic recorded:

| Measure | Epic (599039b) | Source now |
| --- | ---: | ---: |
| Tables | 31 | **33** (`catdex_uploads` and `user_search_migrations` were added later) |
| `v.any()` fields | 22 | 22 |
| Schema `_storage` fields | 9 | 10 (`catdex_uploads.storageId`) |
| Nested storage IDs in JSON | not counted | `palette_generator_settings.config.imageStorageId` |
| `useQuery` / `useMutation` / paginated | 41 / 60 / 1 | 40 / 72 / 3 |
| Server-side caller files | 11 | 11 (17 call sites) |
| Cron jobs | 2 | 5 |
| HTTP route registrations | 2 | 5 |
| `ctx.scheduler` call sites | not counted | 22 |
| Convex functions | not counted | 165 (112 public, 48 internal, 5 HTTP) |

Other facts that shape the design:

- The frontend runs three replicas. The media service, the Discord bot and
  browsers all reach Convex, directly or through frontend API routes.
- The media service calls Convex at `/quick-share/internal`, and Convex pushes
  job IDs to the media worker at `/i/api/internal/jobs/:id`.
- Old links resolve raw Convex IDs in three places: `mapper.getBySlug`
  (`/view/[slug]`, `/api/preview/[id]`), `adoptionV2` batch lookup
  (`/adoption/[slug]`), and `streamSessionsV2.getForHost`.
- Admin allowlists (`QUICK_SHARE_ADMIN_TOKEN_IDENTIFIERS`) and every
  `ownerTokenIdentifier` hold Convex `tokenIdentifier` values, which have the
  form `<issuer>|<subject>`.
- The homelab already runs CloudNativePG (CNPG) for moddrop, Infisical and
  others. Those clusters use daily Longhorn volume-snapshot backups that are
  copied to Garage and pruned after 7 days. No CNPG cluster uses WAL
  archiving, so none has point-in-time recovery.

## Decision

### 1. Forward-only migration

PostgreSQL becomes the source of truth at cutover. There is no write
synchronization back to Convex and no rollback to Convex. Recovery uses
PostgreSQL backups, restore points and forward fixes. Until the cutover
starts, the Convex deployment stays the production system and nothing in
this work changes it.

### 2. Topology

| Environment | PostgreSQL | How it is created | TLS |
| --- | --- | --- | --- |
| Local | One `postgres:18.6-alpine` container per worktree, bound to `127.0.0.1` on a port derived from the worktree path | `pnpm --dir frontend run db:local up` | none (loopback) |
| CI | GitHub Actions service container on `arc-beastypage` (dind), discarded after the job | `.github/workflows/validate.yml` job `database` | none (loopback) |
| Staging | CNPG cluster `beastypage-staging-postgres`, 1 instance, namespace `beastypage-staging`, filled only from the scrubbed archive | kub-homelab change (template in `deploy/postgres/staging/`) | CNPG server certificate, `verify-full` |
| Production | CNPG cluster `beastypage-postgres`, 3 instances, synchronous replication (`any 1`, `dataDurability: required`), namespace `webpage` | kub-homelab change (template in `deploy/postgres/production/`) | CNPG server certificate, `verify-full` |

The homelab manifests live in kub-homelab, not in this repository. The
templates under `deploy/postgres/` are review material for that change; they
are not applied from here. Applying them is a production infrastructure change
and needs explicit approval.

### 3. Roles, credentials, connections and timeouts

Roles:

- `beastypage_owner` owns the schema. Only the migration job uses it.
- `beastypage_app` gets DML on application tables and nothing else. The
  frontend uses it.
- `beastypage_import` is used by the importer during a rehearsal or cutover
  and is disabled afterwards.

Credentials come from Infisical through the existing `InfisicalStaticSecret`
pattern (`/kubernetes/webpage/beastypage-postgres-*`). Nothing is committed.
Rotation: write a new password to Infisical, let CNPG pick up the managed role
secret, then restart the frontend (Reloader already watches the secrets).

The connection URL carries `sslmode=verify-full` and
`sslrootcert=/etc/postgres-ca/ca.crt`, mounted from the CNPG CA secret. In
production the database client refuses to start without TLS unless the host
is a loopback address.

Connection budget (CNPG default `max_connections = 100`):

| Consumer | Connections |
| --- | ---: |
| Frontend pool, 6 per replica × 3 | 18 |
| LISTEN connection, 1 per replica × 3 | 3 |
| Migration job | 1 |
| Importer (cutover only) | 2 |
| Superuser, backup and admin headroom | ≥ 20 |

The budget fits without PgBouncer. PgBouncer in transaction mode would also
break `LISTEN`. If more replicas are added later, put a CNPG `Pooler` in
session mode in front of the pool connections only.

Timeouts (set per role with `ALTER ROLE … SET`, and again in the client):

| Setting | `beastypage_app` | owner / import |
| --- | --- | --- |
| `statement_timeout` | 5 s | 0 (migrations), 5 min (import) |
| `lock_timeout` | 2 s | 10 s |
| `idle_in_transaction_session_timeout` | 10 s | 60 s |
| Client connect timeout | 5 s | 10 s |

### 4. Schema ownership, migrations and version compatibility

- The Drizzle schema in `frontend/server/db/schema/` is the only source for
  table definitions. `drizzle-kit generate` writes SQL to `frontend/drizzle/`,
  and every migration is reviewed and committed.
- CI applies all migrations to an empty database twice (the second run must
  do nothing) and runs `drizzle-kit generate` again to prove the committed SQL
  matches the schema (drift check).
- Migrations follow expand → migrate → contract. A release never drops or
  renames something that the previous release still reads.
- The migration runner (`frontend/scripts/db/migrate.ts`) does the following:
  1. Takes `pg_advisory_lock` on a fixed key, so concurrent runs queue
     instead of racing.
  2. Refuses to run if the database is already at a newer schema version than
     the image knows. It never downgrades.
  3. Applies pending migrations, then records the version, the
     `compatible_from` floor and the application version in
     `beastypage_schema_version`.
- Every build embeds `SCHEMA_VERSION`, the newest migration it ships. At
  startup the application checks
  `db.version >= SCHEMA_VERSION && SCHEMA_VERSION >= db.compatible_from`.
  If the check fails, readiness fails and data routes answer 503. A pod with
  an incompatible schema never serves traffic.
- `frontend/drizzle/compat.json` maps each contract migration to the oldest
  schema version that may still run against it.
- In Kubernetes the runner is a Job, or a Helm pre-upgrade hook, that uses
  the owner role. Application pods never run DDL.

### 5. IDs and legacy URL compatibility

- Every table has `id uuid primary key`.
- New rows get `gen_random_uuid()`, a random v4 UUID. Storage-backed and
  capability-like IDs must stay unguessable, so v7 time-ordered UUIDs are not
  used.
- Imported rows get `uuidv5(NAMESPACE, "<table>:<convexId>")`. This is
  deterministic, so:
  - Imports are idempotent and reproducible on an empty database.
  - Embedded references are rewritten by the same pure function. No lookup
    table is needed while importing.
  - Two runs produce byte-identical rows.
- Every imported table keeps `legacy_id text unique` with the original Convex
  `_id`. `_storage` IDs map the same way into `files.legacy_id`.
- The three legacy lookups become "slug, otherwise `legacy_id`, otherwise
  UUID". Contract tests cover `/view/<convexId>`, `/api/preview/<convexId>`,
  `/adoption/<convexId>` and host links for stream sessions.
- `_creationTime` becomes `legacy_created_at timestamptz` (Convex stores
  float milliseconds; it is rounded to microseconds, PostgreSQL's precision).
  Ties are ordered by `id`. Existing `createdAt`/`updatedAt` number fields
  become `timestamptz` columns with millisecond precision.

### 6. Table classes

Each table falls into exactly one class. The class decides import and
retention behavior. The per-table contract is in
[`data-contract.md`](data-contract.md).

| Class | Tables | Import rule |
| --- | --- | --- |
| Durable product data | card_season, rarity, catdex, collection, coinflipper_scores, cat_profile, cat_images, cat_shares, single_cat_settings, adoption_batch, perfect_cats, perfect_votes, palette_generator_settings, pixelator_settings, dash_settings, discord_user_configs, ancestry_tree, users, user_variants, cat_stream_sessions (settings), wheel_spins, quick_share_uploads (metadata), quick_share_bans | Every row, validated |
| Live session state | stream_sessions, stream_participants, stream_votes, cat_stream_sessions (command and live state) | Every row; command and live state are reset to idle at cutover |
| Short-lived capabilities | discord_challenge, perfect_matchups, catdex_uploads | Only rows still unexpired at the freeze timestamp |
| Queue and work | quick_share_jobs, quick_share_parts | Pending jobs imported. Leased jobs return to pending, because workers are drained. Parts only for uploads still `uploading`. |
| Counters and windows | quick_share_usage | Only windows still open at freeze |
| Migration bookkeeping | user_search_migrations | Not imported. The importer computes `username_search` for every user, so the backfill cron is retired. |

New operational tables: `files`, `live_events`, `jobs`, `job_runs`,
`beastypage_schema_version`, and the importer's own `import_runs`,
`import_checkpoints` and `import_quarantine`.

### 7. File storage

- Bytes move into a `files` table: `id`, `legacy_id`, `sha256` (unique),
  `mime_type`, `byte_size`, `width`, `height`, `bytes bytea`, `created_at`.
  Rows are deduplicated by `sha256`. Normal queries never select `bytes`.
- Every schema-level `_storage` field becomes a `uuid` foreign key to
  `files(id)` with `ON DELETE RESTRICT`. The nested
  `palette_generator_settings.config.imageStorageId` is rewritten to a file
  UUID during import.
- Files are served at `GET /api/files/<id>` with
  `ETag: "<sha256>"`, `Cache-Control: public, max-age=31536000, immutable`,
  `If-None-Match` → 304, and `Content-Length`.
  - Unreferenced files return 404.
  - Staged catdex uploads are never served.
  - This matches today's model: Convex storage URLs are public capability URLs.
- Orphan collection: a daily job deletes files that no row references and
  that are older than 24 hours.

**Gate before #110 closes.** `bytea` stays only if the measured export (#106)
shows:

- total file bytes ≤ 5 GiB,
- 99th-percentile object ≤ 10 MiB,
- a measured restore of the full volume within the RTO below.

If any limit fails, the bytes go to the existing Garage S3 store. The `files`
table keeps the metadata and the serving route stays the same. No new storage
system is introduced either way. Quick Share bytes stay in the media
service's S3 bucket; only their metadata moves.

### 8. Server-side boundaries

```
browser ──HTTP──► app/api/** route handlers ──► server/services/* ──► server/repositories/* ──► server/db (Drizzle, pg Pool)
bot, media ─HTTP─┘   (zod input, auth context)   (authz, transactions)    (SQL only, take a tx)
```

- Everything under `frontend/server/` starts with `import "server-only"`. A
  browser bundle cannot import it, and a browser can never open a database
  connection.
- Route handlers parse input with zod, build an `AuthContext`, call one
  service function and map typed errors to HTTP status codes.
- Services own authorization and transactions. Repositories run SQL and
  nothing else.
- Error contract: `{ "error": string, "code": "not_found" | "forbidden" | "invalid_input" | "conflict" | "rate_limited" | "unavailable" }`
  with statuses 404, 403, 400, 409, 429 and 503. `error` stays a plain
  string because existing clients read `body.error` as the message.
- Isolation is `READ COMMITTED` by default. Read-modify-write sequences such
  as votes, wheel spins, Quick Share admission and job leases take
  `SELECT … FOR UPDATE`, or run at `SERIALIZABLE` with a bounded retry on
  `40001`.
- Idempotency: create endpoints accept a client request ID where Convex
  callers retried. Unique constraints enforce what Convex enforced in code.
- Pagination uses keyset cursors on `(created_at, id)`, encoded as opaque
  base64 strings. This replaces `usePaginatedQuery`.
- Rate limits keep their current semantics and move from Convex tables to
  PostgreSQL rows.
- Browser code uses TanStack Query for fetching and caching, and live topics
  invalidate or replace the cached data. It is added when the first area
  moves (#113), not before.
- During #113 a staging-only flag `DATA_BACKEND=postgres|convex` selects the
  implementation per area. Old and new can then be compared against the same
  fixtures without changing the public API. The flag is removed at cutover.

### 9. Authentication and Clerk identity

- Clerk stays the identity provider.
- Server code reads the session with `auth()` from `@clerk/nextjs/server` and
  builds `tokenIdentifier = "<iss>|<sub>"`. This is exactly the string Convex
  stored, so imported owner columns, `users.token_identifier` and admin
  allowlists keep working unchanged.
- The importer rejects (quarantines) any identifier whose issuer is not the
  configured production issuer.
- Other credentials move unchanged and are checked the same way: overlay
  `?key=` API keys, edit tokens, ancestry password hashes, the Discord service
  token, the Quick Share internal token, and preview refresh tokens.
- Comparisons use `crypto.timingSafeEqual`.
- Parity tests run the Convex implementation (`convex-test`) and the
  PostgreSQL implementation against the same fixtures, including denial cases
  and malformed input.

### 10. Live updates

Convex pushes the latest query result. It does not deliver every
intermediate state. The overlay already guards on the command `seq`. The
replacement keeps the same "latest state wins" semantics on a durable
sequence:

1. Every write to a live aggregate (`cat_stream_sessions`, `stream_sessions`
   and its participants and votes, `wheel_spins`) runs in one transaction
   that:
   - bumps the aggregate's `revision`,
   - inserts `live_events(id bigserial, topic, revision, created_at)`,
   - calls `pg_notify('beastypage_live', topic)`.

   PostgreSQL delivers the notification only when the transaction commits.
2. Each frontend replica holds one `LISTEN` connection. Clients connect with
   Server-Sent Events to `GET /api/live/<topic>`. The request is authorized
   with exactly the same check as the matching read: overlay API key, viewer
   key or Clerk owner. A client cannot subscribe to another session's topic.
3. On connect, the server sends the current snapshot with `id: <revision>`.
   After that, each notification for the topic re-reads the snapshot through
   the same authorized read and sends it if its revision is newer.
4. Missed notifications: the pod remembers the highest `live_events.id` it
   has processed. After a `LISTEN` reconnect it reads every event above that
   ID and refreshes those topics. If the gap is older than event retention
   (1 hour), it reloads every subscribed topic.
5. Clients reconnect automatically with `Last-Event-ID`. They ignore any
   snapshot whose revision is not greater than the one they hold, which
   removes duplicates and stale data. A pod restart or rebalance is just a
   reconnect.
6. Heartbeat comments go out every 15 s so proxies do not close idle
   streams. The server ends each stream after 15 minutes so connections
   rebalance across replicas.
7. NOTIFY payloads contain only the topic. No cat data or images go through
   NOTIFY.
8. Target: control → overlay latency at p95 ≤ 250 ms in the cluster, and
   < 1 s as the hard requirement from #114. This is measured in the
   three-replica test.

### 11. Jobs, schedules and HTTP routes

The `jobs` table replaces both the Convex scheduler and the Convex crons:

- Columns: `kind`, `dedupe_key`, `payload jsonb` (validated per kind),
  `status pending|running|done|dead`, `attempts`, `max_attempts`,
  `run_after`, `lease_owner`, `lease_expires_at`, `last_error`.
- Unique on `(kind, dedupe_key)` while the job is not finished.

How jobs run:

- Each frontend replica runs a job worker, started from
  `instrumentation.ts`. It can be turned off with `JOBS_ENABLED=0`.
- Workers claim jobs with `FOR UPDATE SKIP LOCKED` and hold a time-boxed
  lease. A job is never processed twice at the same time.
- Workers wake on `NOTIFY beastypage_jobs`, which is sent in the enqueuing
  transaction. They also wake at the earliest `run_after` time. There is no
  fixed-interval polling. One recovery sweep every 10 minutes reclaims
  expired leases.
- Failures retry with exponential backoff (5 s → 1 h, jittered), up to
  `max_attempts`. After that the job becomes `dead`: it stays in the table,
  appears in `/api/internal/jobs/status`, and logs an error line that alerting
  can match.
- Recurring work is a singleton job. Each run enqueues its own next
  occurrence through `ON CONFLICT (kind, dedupe_key) DO NOTHING`. A replica
  that starts also inserts any missing singletons. The schedule survives
  every replica restarting.
- Every run writes to `job_runs`: kind, duration, outcome and counts.

| Convex today | Replacement |
| --- | --- |
| cron `username-search-backfill` (6 h) | Retired. The importer fills `username_search`, and the column is `NOT NULL`. |
| cron `catdex-thumbnail-backfill` (6 h, limit 25) | Recurring job, 6 h. Primary path is a `catdex.thumbnail` job enqueued at write time. |
| cron `catdex-upload-retention` (1 h, limit 100) | Recurring job, 1 h |
| cron `quick-share-retention` (1 h) | Recurring job, 1 h. S3 deletes go through `quick-share.dispatch` jobs. |
| cron `perfect-matchup-retention` (1 h) | Recurring job, 1 h |
| `scheduler.runAfter` (22 sites) | `jobs` rows with `run_after`. The batch-cull verdict and the evolution hold release use delayed jobs keyed by session. |
| HTTP `POST /api/storage/getUploadUrl` | `POST /api/catdex/upload-url` |
| HTTP `POST, OPTIONS /catdex/upload` | `POST, OPTIONS /api/catdex/upload`, with the same CORS rules and size limits |
| HTTP `POST /discord/user-config` | Folded into the existing `/api/discord/user-config`, which then calls the service directly instead of Convex |
| HTTP `POST /quick-share/internal` | `POST /api/internal/quick-share`, with the same action protocol and the same `QUICK_SHARE_INTERNAL_TOKEN` |
| Convex → media `POST /i/api/internal/jobs/:id` | `quick-share.dispatch` job, same request |

Compatibility:

- The media service gets `CONTROL_PLANE_URL`, which falls back to
  `CONVEX_SITE_URL`. Switching the URL is a configuration change, not a
  protocol change, and is deployed before cutover.
- Job IDs in media URLs are opaque strings in both systems.
- The Discord bot only talks to the frontend and needs no change.

### 12. Backup, restore, RPO and RTO

- Production uses the homelab convention, a CNPG `ScheduledBackup` with
  `method: volumeSnapshot` copied to Garage, every 6 hours instead of daily.
  It is pruned by the existing `cnpg-backup-prune` job.
- A manual backup is taken immediately before cutover and before every
  contract migration.
- Targets:
  - **RPO ≤ 6 h.**
  - **RTO ≤ 1 h**, including the `files` volume.
- If the measured restore misses the RTO, or the maintainer wants a lower
  RPO, add the CNPG Barman Cloud plugin with WAL archiving to Garage. That
  gives point-in-time recovery and is a homelab-wide decision outside this
  ADR.
- Restore procedure and rehearsal evidence: [`operations.md`](operations.md).

### 13. Cutover outline

The full runbook is written in #116. In short:

1. Rehearse in staging with the scrubbed archive.
2. Take a final PostgreSQL backup.
3. Enable the maintenance gate. The frontend, bot routes, media control
   plane, uploads and jobs reject writes.
4. Pause the Convex deployment and drain the media workers.
5. Record the freeze timestamp, and verify in the Convex logs that no write
   happened after it.
6. Take the final Convex export and import it.
7. Verify counts, hashes, relationships and API comparisons.
8. Switch configuration atomically to the PostgreSQL release.
9. Run the smoke checks, then lift the gate.

Every failure has one of three actions: stay in maintenance, restore
PostgreSQL, or apply a forward fix. Convex is never written again.

## Consequences

- The frontend owns the database. The Discord bot and the media service keep
  talking only to frontend HTTP routes.
- Three new operational duties: watch backups, review migrations, and watch
  dead jobs.
- Live updates become our code. The three-replica test in #114 is required
  before cutover.
- Whether `bytea` holds is open until the production sizes from #106 are
  measured.

## Not decided here

- The production export (#106) needs the maintainer. It costs Convex
  bandwidth and creates a sensitive archive.
- Where the encrypted archive is stored, who owns it, and how long it is kept.
- The kub-homelab change for staging and production clusters, which needs
  approval.
